> below are historical Stage 6 notes and no longer describe the local
> candidate source. The up-to-date behavior and deployment boundary are in
> [STAGE_11_CORRECTNESS_AUDIT.md](STAGE_11_CORRECTNESS_AUDIT.md). In
> particular, the candidate now permits one challenge per verdict attempt,
> freezes policy timing/evidence constraints, validates evidence references
> and uncertainty in equivalence, reverses reputation when a finalized
> verdict is superseded, enforces delegated evidence permission, restricts
> cancellation and settlement states, and waits for finalized successful
> transaction receipts in the frontend. **These candidate changes are not
> present on the live V1 or V2 addresses.**

## Open risks (stated plainly, not smoothed over)

1. **No challenge bond.** Because real GEN custody is disabled by default (section 5 of `PROTOCOL_ARCHITECTURE.md`), `challenge_verdict` cannot require a forfeitable bond without contradicting the "no fake escrow" invariant. A production deployment that re-enables `settlement_native_transfer_enabled` should also add a bonded-challenge path before handling meaningful value — not present in this build.
2. **Admin centralization for module registry and challenge resolution.** A single admin key currently decides module registration and challenge outcomes. This is explicitly flagged in `PROTOCOL_ARCHITECTURE.md` section 6 and is the honest reason features 12 (Precedent), 17 (Negotiation), and 20 (Collusion Detection) are not implemented — they would need a real decentralized-jury design this session did not have the scope to build and verify. **Stage 6 partial mitigation (source only, see item 8 above):** `resolve_challenge_by_timeout` removes the admin's ability to indefinitely block finalization through inaction, but does not reduce the admin's discretionary power to decide a challenge's merits *while still within the deadline* — that centralization is unchanged.
3. **Source substitution between leader and validator fetch.** If a target server serves different content based on request timing/IP/headers, the validator's independent re-fetch is the only defense, and it is a weak one against a sophisticated adversary. No stronger defense (e.g., signed evidence commitments with a reveal window — feature 36) is implemented yet; it is designed in the spec but not built this session.
4. **Sybil-resistant reputation (feature 40) not implemented.** See table row above.
5. **genvm-lint / Studio runtime version mismatch.** A clean lint pass does not prove Studio will load the contract (see `GENLAYER_CAPABILITY_MATRIX.md` section 2). No live Studio deployment was performed this session to close this gap.
6. **Time source is this pinned SDK's only option, and is unverified at the real-WASM level.** `_now_dt()` uses `datetime.datetime.now(UTC)` because the pinned v0.2.16-era SDK has no dedicated clock function (`gl.vm.get_timestamp()` was added in a later SDK generation and is absent from this pin — confirmed by reading the extracted pinned SDK's `genlayer/gl/__init__.py`, which exposes only `trace_time_micro()`). A later audit session confirmed, via a new direct-mode test (`tests/direct/test_time_determinism.py`), that `gltest`'s `warp()` cheatcode controls `datetime.datetime.now(UTC)` with exact identity inside this test harness, and found documentary (not independently executed) evidence from the current GenVM spec that the real Wasmtime runtime's WASI time functions are "modified to ensure reproducible behavior across validators" in normal (non-debug) execution. No live WASM-level GenVM execution of this contract was performed to confirm this directly — remains an open verification gap, not a known hazard.
7. **GLSim's deploy-class-cache bug (corrected diagnosis).** A prior session misdiagnosed a GLSim deploy failure as a GLSim stub gap in `glsim/genvm_stubs.py`. An audit session reproduced the failure live and found the real cause: `glsim/engine.py`'s contract-class cache (populated after a successful deploy) caches the wrong class — a calldata-roundtrip proxy wrapper from `gltest/direct/loader.py::_make_contract_proxy`, which prints identically to the real contract class but has no `gl.Contract` base and no `__gl_allow_storage__`. Every deploy after the first one to the same running GLSim server hits this bad cache entry and fails. See `docs/FINAL_HANDOFF.md` section 4.1 for the full root-cause chain. This is SIMULATOR-ONLY (a bug in the `glsim` package itself, not in this contract or the real pinned GenVM SDK). **Update 2026-10-13: confirmed not to affect the real deployment** — the contract deployed successfully to StudioNet (`0xb222305575ee8af1255d8aCd196280b405B54Baf`) and two full agreement lifecycles were run live with no equivalent failure, closing the "not independently live-tested" caveat for this specific concern.
8. **Unbounded challenge-resolution latency (found 2026-10-13 live on StudioNet; FIXED in contract source 2026-10-14, Stage 6 — NOT yet live on the deployed instance).** `resolve_challenge` has no deadline of its own — confirmed by reading `contracts/agentverdict.py` lines 1206-1232, it only checks the challenge is `OPEN` and the agreement is `CHALLENGED`, with no comparison against `verdict.challenge_deadline` or any admin-response SLA. Once a challenge is filed, the agreement leaves `CHALLENGE_WINDOW` for `CHALLENGED` and `finalize_verdict`'s window check (which only applies to `ST_CHALLENGE_WINDOW`) can never reach it again. Live-confirmed on agreement `A-2`: `resolve_challenge` succeeded hours after the original verdict's window would have closed, with no error and no state-based time pressure on the admin.
   **Stage 6 fix (source only; see `docs/STAGE_6_MIGRATION_NOTE.md` for the full rationale and why this cannot reach the live instance):** `Challenge` gained a `resolution_deadline` field, set in `challenge_verdict` to `now + policy.challenge_window_seconds` (reusing the agreement's own policy SLA rather than a new, independently-governed constant). A new permissionless `resolve_challenge_by_timeout(challenge_id)` method lets anyone (deliberately not restricted to a party or the admin — see the method's docstring for the full griefing-risk analysis) unstick a `CHALLENGED` agreement once that deadline passes with the challenge still `OPEN`. The outcome is always deterministic: it **upholds the original verdict** (never auto-upholds the challenge), per spec invariant 8 ("no automatic high-stakes penalties based only on inferred collusion or speculative causality") — admin silence is not evidence of the challenge's merit. It routes through the same `_reopen_challenge_window` effect `resolve_challenge`'s own rejection branch uses (no parallel settlement/reputation logic), and tags `Challenge.state = "TIMEOUT_REJECTED"` (distinct from a normal admin `"REJECTED"`) for an unambiguous audit trail. Covered by `tests/direct/test_challenge_timeout.py` (9 new tests: deadline set on filing, pre-deadline admin resolution unaffected, pre-deadline timeout-call rejected, post-deadline timeout-call succeeds, permissionless-caller success, double-call idempotency, full finalize/reputation-event parity with the normal path, wrong-agreement-state guard, unknown-challenge-id guard).
   **Residual risk, stated plainly:** the already-deployed V1 instance at `0xb222305575ee8af1255d8aCd196280b405B54Baf` does **not** have this fix (GenVM contracts are deployed-code-immutable; see the migration note) — any agreement on that live instance that gets challenged, whose admin never calls `resolve_challenge`, remains exactly as exposed to this gap as before. `A-1` and `A-2` are already `FINALIZED` and therefore unaffected retroactively, but any *future* agreement created on that same deployed address is not protected until a new contract version is deployed to a new address.
   **Update 2026-10-14 — LIVE-VERIFIED on a new V2 deployment, not just in direct-mode tests.** A separate contract instance was deployed to `0xCC67216ceD224A971739bAA706142A740B31853C` (V1 untouched, unaffected) running this exact Stage 6 fix. A real challenge (`C-1` on agreement `A-1`) was filed, deliberately left unresolved past its `resolution_deadline`, and `resolve_challenge_by_timeout("C-1")` was called instead of `resolve_challenge`. It succeeded with real 5/5 validator consensus: `get_challenge` confirmed `state: "TIMEOUT_REJECTED"` with the exact audit-trail message `"[TIMEOUT] admin did not call resolve_challenge before the resolution deadline; original verdict upheld automatically, no discretionary judgment applied"`, and `get_agreement` confirmed the agreement correctly reopened into `CHALLENGE_WINDOW` with a fresh deadline, which was then finalized normally. This closes the gap between "fixed and tested in isolation" and "proven working under real GenVM consensus." Full call-by-call record in `docs/V2_STUDIONET_LIVE_VERIFICATION_REPORT.md`. The V1 residual risk described above is unchanged and still applies to V1 specifically.
9. **Nondet-mode storage pickling warning (found 2026-10-13 live on StudioNet; ROOT-CAUSED and FIXED in contract source 2026-10-14, Stage 6 — NOT yet live on the deployed instance).** Both live `request_evaluation` calls (`A-1` and `A-2`) emitted `UserWarning: Detected pickling storage class. Reading storage in nondet mode is not supported` on stderr, from `/py/libs/genlayer/gl/_internal/storage.py:21`. Both calls still returned `SUCCESS` with correct, validator-agreed results.
   **Root cause, confirmed by reading the pinned v0.2.16 SDK's own source (not guessed):** `gl.vm.run_nondet`/`run_nondet_unsafe` (`genlayer/gl/vm.py`) serialize `leader_fn`/`validator_fn` with `cloudpickle` before executing them. Every `@allow_storage` dataclass instance (e.g. an `EvidencePacket` read out of `self.evidence[eid]`) carries a live `_storage_slot` (`genlayer/py/storage/_internal/desc_record.py::_RecordDesc.get()`), whose `__getstate__` returns `(self.manager, self.id)` (`genlayer/py/storage/_internal/core.py::Slot.__getstate__`) — i.e. pickling ANY storage-backed object also pickles the contract's storage-manager singleton (`_ActualStorageMan`), whose own `__getstate__` override is exactly what prints the observed warning. The contract's `_run_llm_adjudication` built `bounded_rows = evidence_rows[:MAX_EVIDENCE_SOURCES]` — the actual storage-backed `EvidencePacket` objects, not plain values — and captured that list directly inside `leader_fn`/`validator_fn`, the closures `gl.vm.run_nondet` pickles. This was a contract-side defect, not a GenVM/SDK limitation: fixed by extracting plain `str` fields into ordinary dicts strictly before `leader_fn` is defined, so the closures only ever capture plain Python immutables.
   **Reproduction, executed this session (not assumed):** a standalone script using the pinned SDK's real `Slot`/`Manager` classes confirmed the vulnerable pattern fires the exact warning text and the fixed pattern does not (kept in the suite as `tests/direct/test_storage_pickling_regression.py::test_real_sdk_slot_pickling_mechanism`). Separately confirmed, and recorded explicitly rather than assumed: `gltest`'s direct-mode test harness (`InmemManager`) has no `__getstate__` override at all, so it cannot reproduce this warning via `request_evaluation` either way, even with the harness's own `check_pickling=True` cheatcode enabled (`tests/direct/test_storage_pickling_regression.py::test_direct_mode_check_pickling_is_silent_either_way`) — direct-mode silence on this specific issue was never evidence of safety.
   **Consensus/correctness impact assessment:** no validator-consensus or state-persistence defect was found — the pickled closure's `Slot`/manager reference round-trips correctly inside the real runtime's leader/validator process (both live calls returned correct, validator-agreed results), so this was never silently producing wrong results. The risk was reliance on an undocumented, explicitly-unsupported code path ("Reading storage in nondet mode is not supported") that the SDK's own authors flag as fragile, not a demonstrated live defect. Fixed proactively rather than left as a known-but-tolerated warning.
   **Update 2026-10-14 — LIVE-VERIFIED on the V2 deployment (`0xCC67216ceD224A971739bAA706142A740B31853C`).** Three separate live `request_evaluation` calls on V2 (two on `A-1` across its rework cycles, one on `A-2`) all returned **empty stderr** — no pickling warning — versus the warning appearing on both of V1's live calls under the pre-fix source. This is real observed behavior across three real consensus rounds, not a single lucky result, and is strong (though not mathematically exhaustive across every possible future input) live confirmation that the fix holds under real GenVM, not only in the standalone reproduction script. Full call-by-call record in `docs/V2_STUDIONET_LIVE_VERIFICATION_REPORT.md`.
